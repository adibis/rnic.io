## Locator

![The master RNIC block diagram with the MR/Key Table highlighted and Key Cache dimmed -- this chapter writes a new entry into that table for the first time.](/images/mr/04-registering-a-memory-region-locator.svg)

[The Key Table](/mr/the-key-table) covered the MPT/MTT structure a memory region's entry lives in once it exists. This chapter covers how it gets there.

## Overview

Registering a Memory Region is conceptually the same act as installing a page-table mapping and pinning those pages against eviction or swap, just performed once, explicitly, for a range about to be exposed outside the process's own instruction stream instead of continuously for the process's own working set. A Queue Pair climbs through a hardware-enforced sequence of states before it can carry a single packet -- RESET, INIT, RTR, RTS, each transition its own gate. A memory region doesn't. It is registered, at which point its `lkey` and `rkey` are immediately usable in a Work Request, or it is deregistered, at which point they are not. There is no INIT-equivalent holding state, no negotiated handshake with a peer, no multi-attribute mask a driver assembles across several calls. This chapter covers the entire lifecycle -- registration, validity, deregistration -- in one place, in place of a separate state-machine chapter, precisely because the underlying lifecycle doesn't have [QP State Machine](/qp/qp-state-machine)'s richness to justify splitting it up the same way.

## Deep walkthrough

**What `ibv_reg_mr` actually costs, and why the manual doesn't say.** The call takes a Protection Domain, a virtual address range, and a set of access flags, and returns a populated `struct ibv_mr` carrying an `lkey` and `rkey` (2.1). What it does to get there -- same abstraction-boundary gap this book has already hit at [Part 0](/overview/) (Overview)'s doorbell and [Part 1](/qp/) (Queue Pair Management)'s QP table organization -- is not described at the verbs-manual level. The verbs API is deliberately a boundary: software states what it wants registered and gets back keys, and the real cost sits entirely on the driver/hardware side of that boundary. Architecturally, what has to happen is not in serious doubt even without a vendor's exact sequence to cite: the process's page tables get walked to resolve the requested virtual range down to physical pages, those pages get pinned so the OS can no longer swap or relocate them out from under a device that holds direct physical-address translations to them, and the MR/Key Table (2.2) gets populated -- an MPT entry recording address, length, and permissions, plus one or more MTT entries covering however many physical pages the registration spans. None of that is this book asserting a specific implementation's exact op sequence; it's the minimum architectural work a "return a valid, hardware-usable key" contract has to do.

**Valid or invalid -- not a state machine.** Once registration completes, the MR is valid: its keys can appear in a local Work Request or be handed to a remote peer immediately, with no further transition to wait through. [QP State Machine](/qp/qp-state-machine) exists because a QP needs a port bound, a partition-key index supplied, and a peer named before it's safe to use -- three separate hardware-enforced gates. A memory region has none of that to negotiate; the moment its table entry is populated, its keys are live. Deregistration (`ibv_dereg_mr`) is the only other transition this object has: it removes the MPT/MTT entries and retires the keys. That's the entire lifecycle -- two states, not five -- and it's worth saying plainly rather than leaving a reader who just finished Part 1 wondering where this book's version of the QP state machine went. It didn't get skipped; the object underneath it genuinely doesn't have that shape.

**On-Demand Paging: the real alternative to pinning upfront.** Setting `IBV_ACCESS_ON_DEMAND` at registration creates an MR that skips upfront page pinning entirely. `ibv_reg_mr(3)`'s exact recipe for the common *implicit* ODP case -- one MR covering a process's entire address space rather than one fixed range -- is specific and worth quoting directly: "`IBV_ACCESS_ON_DEMAND` should be set, `addr` should be 0 and `length` should be `SIZE_MAX`." The tradeoff this makes is real and worth naming precisely: a pinned registration pays its full cost once, upfront, at `ibv_reg_mr` time, and every access after that is guaranteed not to stall on a page fault. An ODP registration pays close to nothing at registration time and instead defers that cost to first touch -- the first access to a given page triggers a page-fault-style resolution, handled cooperatively by hardware and driver against the OS's own page tables, exactly when that page is actually needed rather than speculatively for the whole range up front. This is the same shape as a demand-paged TLB miss handler, just triggered by a network-visible access instead of a local one -- the first touch, not registration time, is when the real cost lands. That's a genuine latency-shape tradeoff, not a strictly better option: ODP is attractive when a registered range is large relative to what actually gets touched, or when registration-time latency matters more than a possible stall later; pinned registration is attractive when every page will be touched anyway and a predictable, fault-free access pattern matters more than registration speed. This chapter's main treatment stays on the standard pinned path, consistent with this book's current scope -- ODP gets this one paragraph as a real, named alternative, not a second full treatment. One consequence worth flagging plainly rather than leaving implicit: implicit ODP's whole point is covering a process's *entire* address space with one registration, which means a single successfully-guessed or leaked `rkey` for an implicit-ODP region exposes the whole process, not one buffer -- a materially larger blast radius than the bounded-range case [Permission and Bounds Violations](/mr/permission-and-bounds-violations) covers next, worth carrying forward into that chapter's own reasoning about what a bad `rkey` can actually reach.

**Memory Windows: a related but distinct mechanism, out of scope here.** `IBV_ACCESS_MW_BIND` appeared in the access-flags table two chapters back, and it's worth naming precisely why it gets no further treatment in this chapter: a Memory Window is not a Memory Region. Where an MR is registered once, through the relatively heavyweight path this chapter just walked, and stays valid until explicitly deregistered, a Memory Window is a lightweight sub-scope carved out of an *already-registered* MR -- its own `rkey`, its own narrower address range or access-rights subset, created and torn down through a cheap bind/rebind/invalidate operation rather than a full registration cycle. The real use case is letting software narrow or revoke a remote peer's access to part of an already-registered region without paying deregistration's cost every time -- a genuinely different tool built for a different job (fine-grained, frequent scope changes) than what this chapter's registration path is built for (coarse-grained, infrequent). Memory Windows are scoped out of this book's first pass the same deliberate way ODP's implicit/explicit distinction and the newer `IBV_ACCESS_FLUSH_*` flags are -- named here so a reader who knows the flag exists doesn't wonder if it was simply missed.

**Deregistration: removing the entry, not the responsibility.** `ibv_dereg_mr` reverses registration -- the MPT/MTT entries are removed from the table (and from the Key Cache, 2.3, if resident there) and the keys are retired. What it does not do is guarantee anything about operations already in flight that reference those keys, or protect against software that keeps using a retired key after the call returns; that's [Permission and Bounds Violations](/mr/permission-and-bounds-violations)'s subject next, not this chapter's.

> **Design rationale.** Pinning pages at registration time rather than defaulting every MR to ODP-style lazy resolution is a deliberate choice about where to put a cost that has to be paid somewhere. Upfront pinning makes every subsequent access to that region fault-free and its latency predictable -- exactly what a performance-sensitive RDMA path wants, since a stall on the data path is precisely what registration exists to move out of the way in the first place. The cost is that registration itself becomes proportional to region size, paid whether or not the whole region ever actually gets touched. ODP inverts that trade: registration is cheap regardless of size, but the first-touch cost is deferred, not eliminated, and lands unpredictably wherever an access pattern first reaches a given page. Neither option is free; the choice is really about which latency a given workload can afford to have -- a known one, paid once, or a smaller, spread-out one, paid on demand.

## Interface / timing reference

| Step | What happens | Cost model |
|---|---|---|
| `ibv_reg_mr` (default, pinned) | Walk process page tables, pin pages, populate MPT + MTT entries, assign `lkey`/`rkey` | Upfront, proportional to region size / page count -- exact figure not disclosed at verbs level |
| `IBV_ACCESS_ON_DEMAND` (explicit ODP) | Upfront pinning skipped for the named range | Deferred to first touch, page-fault-style |
| Implicit ODP recipe | `addr = 0`, `length = SIZE_MAX`, `IBV_ACCESS_ON_DEMAND` set | Covers the entire process address space lazily, one registration |
| `ibv_dereg_mr` | MPT/MTT entries removed, keys retired | Software must stop using the retired keys itself -- not hardware-enforced (2.5) |

Registration and deregistration are what put keys into circulation and take them back out. What happens when a key that's still in circulation gets presented for an operation it was never granted, or against an address range outside what it covers, is [Permission and Bounds Violations](/mr/permission-and-bounds-violations)'s subject next.
