## Overview

[Key Cache Eviction Policy](../key-cache-eviction-policy) named two independent mechanisms living in the same satellite block: ordinary capacity-pressure eviction, which picks one victim translation at a time, and mass invalidation on memory-region deregistration, which clears the working set wholesale with no victim selection at all. This chapter asks what actually runs each one. The first question is identical to one this book has already answered; the second is new.

## Deep walkthrough

**Capacity-pressure eviction runs on the same spectrum [Part 1](/qp/) (Queue Pair Management) already built.** [Hardware-Assisted Eviction Engines](/qp/hardware-assisted-eviction-engines) worked through the full fixed-function/programmable/software-driven tradeoff for the QP Cache, and because [Key Caching](../key-caching) already established that this is the identical shared SRAM, not a separately-designed structure, that entire analysis carries over to MTT/MPT eviction without modification: the same latency-versus-flexibility spectrum, the same reasoning about why a programmable-but-hardware-resident engine is the realistic middle ground most designs reach for, the same conclusion that a software trap on every miss reintroduces the round-trip RDMA hardware offload exists to remove. This book isn't re-deriving that spectrum a second time for a second resource type sharing the same cache; [Hardware-Assisted Eviction Engines](/qp/hardware-assisted-eviction-engines) is the one place it's argued, and it applies here exactly as written.

**Mass invalidation is not a smaller version of eviction — it's a different operation entirely.** Ordinary eviction, however it's decided, always has the same shape: pick one occupied slot, write it back if dirty, free it, fill it with the incoming translation. A mass invalidation triggered by `ibv_dereg_mr` has none of that shape. There is no incoming translation waiting for the freed space, no victim to select among candidates, no policy input to consult — the entire cache's occupied MTT/MPT slots (or some large, unpredictable subset of them, per [Key Cache Eviction Policy](../key-cache-eviction-policy)'s finding that a real RNIC is reasoned to flush wholesale rather than sweep out only the deregistered entries) simply stop being valid at once. The hardware mechanism this actually needs is closer to a global clear or a broadcast invalidate signal than to anything resembling a victim-selection engine — cheaper to build, in the sense that it needs no policy logic at all, but not cheaper to execute, for a reason the next paragraph gets into.

**What a flush actually has to coordinate with.** A tag-clear that happens instantaneously, with no regard for what else is touching the cache at that moment, is the simplest possible implementation and also the most dangerous one. [Shared-MR Arbitration](../shared-mr-arbitration) already named the general version of this problem: a lookup already in flight against an entry that a concurrent invalidation is in the process of clearing can, in principle, either complete against a translation that's being retired underneath it or be interrupted partway through. [Mid-Transaction Deregistration](../mid-transaction-deregistration) sharpens that same question specifically for a DMA burst that has already resolved its translation and is actively moving bytes when the flush hits. Neither chapter resolves whether real hardware fences the flush against in-flight lookups (stall new lookups, drain the ones already running, then clear) or lets the flush proceed unconditionally while accepting that a lookup mid-flight might observe a half-torn-down cache — and this chapter doesn't resolve it either; there is no public source describing which choice any real RNIC makes. What this chapter adds is the cost framing: an eviction engine that fences against in-flight work pays that cost once per single-entry eviction, a rare, already-expensive event; an invalidation engine that has to fence the same way pays it across every occupied slot at once, on every `ibv_dereg_mr` call, which is a categorically larger and more frequent tax if the fencing is real.

**Why this is the one place [Part 2](/mr/) (Memory Region / Key Table)'s hardware question is new.** Every other chapter in this Part has been the same checklist item Part 1 already worked through, applied to a different resource, with mostly the same answer available by cross-reference. This is the exception: Part 1's QP Cache never had an operation that invalidates its entire working set as a side effect of one control-plane call on one QP, because tearing down a single QP was never reasoned to touch any other QP's cached context. Memory regions are different — deregistering one is reasoned to cost every other resident translation, unrelated MRs included, exactly the asymmetry [Key Cache Eviction Policy](../key-cache-eviction-policy) already quantified. The eviction-engine question Part 1 answered stays answered here. The flush-engine question has no Part 1 analog to point back to.

> **Design rationale.** A design that fences the mass-invalidate against every in-flight lookup buys correctness — no lookup ever observes a translation that's simultaneously being torn down — at the cost of turning an unrelated application's `ibv_dereg_mr` call into a latency event for every other tenant currently touching the cache, however briefly. A design that doesn't fence buys speed and isolation between tenants at the cost of an unresolved race whose actual behavior on real silicon isn't documented anywhere this book found. The asymmetry that makes this a harder call than it looks: an eviction engine's fencing cost is paid by the one workload that caused the pressure, but an invalidation engine's fencing cost, if it exists, is paid by every workload sharing the cache at the moment one of them happens to deregister a region — a blast radius in *time* (stalling unrelated lookups) layered on top of the blast radius in *space* ([Key Cache Eviction Policy](../key-cache-eviction-policy)'s wholesale-flush finding) this Part has already established. Neither this chapter nor any source it could find says which tradeoff a real vendor actually made.

[Mid-Transaction Deregistration](../mid-transaction-deregistration) closes this Part by taking the fencing question from a cache-wide concern to a single DMA burst's concern: what happens to one transfer, already in progress, when the translation it depends on disappears out from under it mid-burst.
