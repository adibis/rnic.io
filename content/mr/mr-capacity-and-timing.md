## Overview

[The Key Table](/mr/the-key-table) named a hard ceiling on registrations and moved on; [Key Caching](/mr/key-caching) named a shared, cross-resource working-set pressure and moved on too. Neither chapter asked what a "maximum registered MR count" even means once a registration's real cost depends on how large it is, not just that it exists. This closing chapter asks that question, then asks a second one this part has left completely open: how a slow, infrequent registration call and a fast, constant per-DMA key resolution end up touching the exact same structure safely -- and, along the way, answers the open question [Registering a Memory Region](/mr/registering-a-memory-region) raised without resolving: whether a key can ever become resolvable before every MTT entry behind it actually exists.

## Deep walkthrough

**"How many MRs" is the wrong question to start with.** [The QP Table](/qp/the-qp-table) answers a flat question: one QP costs one table entry, so "maximum QP count" and "table size" are the same number. The Key Table doesn't work that way. One MR costs one MPT entry plus however many MTT entries its registration spans -- [Registering a Memory Region](/mr/registering-a-memory-region) already established that an MTT entry exists per physical page the registration covers, and that registration cost is proportional to region size, not a flat per-call charge. (Some real implementations likely reduce that per-page ratio for a large contiguous range by covering it with fewer, larger-granularity translation entries -- a superpage-style optimization in the same spirit as a CPU's own large-page TLB entries -- but no source found pins down whether or how any specific RNIC supports that, so treat it as a plausible refinement, not an established fact.) A chip that can hold ten thousand small, single-page registrations might only hold a few dozen registrations the size of implicit ODP's whole-address-space case before the same MTT storage runs out. There is no single "maximum MR count" independent of what those MRs actually look like -- the real resource being spent is total MTT entries, and MR count is just one way of spending it.

> [!CAUTION] Gotcha
> A chip's published "maximum registered regions" figure, if one exists, is only meaningful next to an assumed average registration size. A workload that registers few, huge ranges and a workload that registers many small ones can exhaust the identical underlying MTT storage at wildly different MR counts. Don't read a max-MR number as a flat ceiling the way [The QP Table](/qp/the-qp-table)'s max-QP number actually is one.

**The one ceiling that is flat: MPT entries.** Permission-and-bounds metadata -- address, length, access flags, per [The Memory Region Descriptor](/mr/the-memory-region-descriptor) -- is a fixed-size record regardless of how many pages the registration covers, so the MPT half of this table does impose a flat ceiling on registration *count*, independent of size. A registration can fail two different ways against two different limits: out of MPT entries (too many distinct registrations, regardless of their size) or out of MTT entries (registrations too large in aggregate, regardless of how few there are). Software sees one failure either way -- a rejected registration call -- with no guarantee it can tell which limit it hit.

**Where this connects to Part 1's version of the same question.** [QP Capacity and Timing](/qp/qp-capacity-and-timing) argued that a real max-QP number is the minimum across several *hard*, per-QP-allocated resources owned by different parts of this book, and that the QP Cache's soft working-set bound doesn't belong in that count at all. The Key Table side of that argument is narrower: nothing about what a memory region actually is -- a target range, not a connection with its own send schedule, retry state, or injection rate -- suggests it reserves a WQE ring slot, a Replay Buffer share, or a Rate Limiter entry the way a QP does. Parts 3, 5, and 6 aren't drafted yet, so this book can't rule out some hard-allocated resource elsewhere keyed to a live registration the way those chapters key theirs to a live QP, but nothing points toward one either -- MPT and MTT entries are the best-supported hard-ceiling story for this resource today, not a confirmed complete one. What *does* cross into other territory is the soft side, and it crosses further than Part 1's did: [Key Caching](/mr/key-caching) already established, with real citations (the uRDMA paper's cache model, corroborated in part by Kong et al.), that the Key Cache isn't just conceptually similar to the QP Cache -- it is the identical physical SRAM, shared with QP context, Completion Queue context, and Event Queue context all at once. A registered-MR population large enough to pressure that shared cache doesn't only slow down other memory-region lookups; it degrades QP context lookups too, and the reverse holds just as this book's Part 1 chapter had to leave unconfirmed for lack of a source -- Part 2's own sourcing settles that question more directly than Part 1's could.

> [!TIP] Why
> Splitting MPT from MTT the way [The Key Table](/mr/the-key-table)'s Analogy callout already compares to a PMP-then-TLB split pays off again here: it's exactly what makes MPT-only and MTT-only exhaustion two different failure modes instead of one. A monolithic per-registration record sized for the worst case (maximum page count) would waste storage on every small registration; splitting the fixed-size protection metadata from the size-proportional translation entries lets a chip provision each independently against the failure mode that actually matters for a given workload -- many small registrations pressure MPT, a few huge ones pressure MTT, and a chip's real capacity planning has to reason about both, not one number.

**Where this is checked, and the open question it finally answers.** Nothing about capacity is checked per DMA. It's checked at registration, against whichever of MPT or MTT entries runs out first, and the software-facing result is a failed registration call -- the same shape [The QP Table](/qp/the-qp-table) already described for its own entries. But [Registering a Memory Region](/mr/registering-a-memory-region) left a sharper question open: whether a key becomes externally resolvable before every MTT entry behind it is actually populated, since registration is a multi-step construction (page tables walked, pages pinned, one MPT entry written, then one or more MTT entries written behind it) -- not a single atomic act. This chapter's timing argument, below, answers that architecturally: no.

**A second question this part has left completely open: timing.** Nothing in this part has asked what clock a Key Table lookup runs on relative to the software call that populated the entry it's reading. Those are two very different kinds of access to the same structure, and, as in Part 1, they don't share a clock domain by default.

**Two write paths -- but only one of them writes on the hot path.** Here the Key Table's story diverges from the QP Table's. A QP's live state gets *written* by the datapath itself on nearly every packet -- send and receive PSN counters advance continuously ([QP Context](/qp/qp-context)). An MPT/MTT entry has no equivalent on the translation and permission payload itself: the DMA Engine's Address Translation stage only ever *reads* that payload to authorize and route a transfer; nothing about a routine DMA writes back into the address, length, permission, or translation fields it consulted. [Shared-MR Arbitration](/mr/shared-mr-arbitration) already flagged the one asterisk on this claim and left it open rather than resolving it: if an LRU-style eviction policy piggybacks recency metadata onto the same cache line, a read-only lookup does become a write to *that* metadata, even though the translation payload stays untouched -- a question no source resolves, and this chapter doesn't resolve it either. Setting that open bookkeeping question aside, the payload's hot-path side of this crossing is simpler than Part 1's -- a pure read against the data that actually gates a DMA, with no read-modify-write race to reason about there. The control-plane side is where all the payload writing happens: registration populates an entry for the first time, and deregistration retires one, both arriving over a register or command interface almost certainly clocked independently of the DMA Engine's own core datapath clock -- architecturally the same control-plane-vs-datapath split [QP Capacity and Timing](/qp/qp-capacity-and-timing) already named, applied to a resource whose hot-path payload never talks back.

> [!WARNING] Analogy
> A hardware page-table walker only ever reads page-table entries to satisfy a translation; it's the OS, running asynchronously and on its own schedule, that ever writes one. An MPT/MTT entry is read by the DMA Engine exactly that same way -- registration and deregistration are software's equivalent of the OS updating a page table out from under a walker that never itself writes back.

**Why the answer to registration's open question is no.** A registration populating one MPT entry and however many MTT entries a large region requires is precisely the multi-bit, multi-write crossing [QP Capacity and Timing](/qp/qp-capacity-and-timing) already argued a plain synchronizer can't safely carry, and it's a harder version of that problem than a modify-QP call ever was -- a modify-QP request writes one bounded attribute struct; a large registration writes a variable, potentially long chain of MTT entries one at a time. If any of those entries became visible to a concurrent lookup as soon as it landed, a DMA arriving mid-registration could resolve against a torn, partially-populated translation chain -- the construction-side mirror of the teardown race [Mid-Transaction Deregistration](/mr/mid-transaction-deregistration) already covers in depth. No public source confirms this for a real RNIC, but the architecturally sound answer is almost certainly the same shape as Part 1's: the whole chain -- MPT entry and every MTT entry behind it -- gets built in a staging area on the control-plane side of the boundary and only gets swapped into the structure the DMA Engine actually reads once construction is complete, through a handshake, not a bare synchronizer. A lookup that arrives before that swap simply doesn't find the key yet, the ordinary and correct failure mode [The Key Table](/mr/the-key-table) already covers; nothing observes a half-built entry.

> [!IMPORTANT] Food for Thought
> [Mid-Transaction Deregistration](/mr/mid-transaction-deregistration) couldn't resolve whether a real implementation holds a private, already-resolved translation copy for a DMA burst in flight, or re-touches the shared table mid-burst. If a chip already builds the staged/shadow-copy machinery this chapter argues registration needs, does that same machinery make a private per-burst copy on the *teardown* side cheaper to justify, or is it solving an unrelated problem that happens to look similar? Argue both ways.

**Pipeline depth, briefly.** A Key Cache lookup is naturally at least two conditional stages, not one -- [The Key Table](/mr/the-key-table)'s own MPT-then-MTT split, mirrored in [Key Caching](/mr/key-caching)'s working set, means a permission check against the MPT entry has to resolve before it's even meaningful to walk into MTT territory behind it. A rejected permission check can stop after the first stage; only a lookup that's actually authorized to move data pays for the second. This book states that shape as reasoned inference about how a two-part structure like this is ordinarily pipelined, not a specific vendor's cycle count; the DMA Engine's own scatter-gather walk once a translation is in hand belongs to Part 8, forward-referenced here rather than re-derived.
