## Overview

[Mid-Transaction QP Reset](/qp/mid-transaction-qp-reset) closed [Part 1](/qp/) (Queue Pair Management) on the same shape of question this chapter closes [Part 2](/mr/) (Memory Region / Key Table) with: a resource torn down while something is still actively using it. There, the resource was a Queue Pair and the thing still in flight was a packet, a replay-buffer entry, a partially-reassembled message. Here, the resource is a Memory Region and the thing still in flight is a DMA burst that has already resolved an `rkey` against the key table and started moving bytes, at the exact moment software calls `ibv_dereg_mr` on the other end of that same MR. Same shape, different resource, and — unlike Part 1's version — one real, sourced anchor to start from before the chapter has to reason on its own.

## Deep walkthrough

**What the contract actually says.** RDMAmojo's documentation for `ibv_dereg_mr()` is direct about where responsibility sits: "It is up to the user to stop using the keys (lkey and rkey) that are associated with this MR. If those keys will be used in local Work Requests or by remote operation requests, it will lead to Work Completion errors." That sentence is this chapter's one solid factual anchor, and it is worth being precise about what it does and doesn't establish. It establishes that avoiding a stale-key access is a software obligation — synchronize with the remote peer, drain outstanding operations, *then* deregister — not a condition hardware is documented to detect and safely reject on its own. It does not establish what a stale-key access actually produces at the hardware level if the contract is violated anyway. RDMAmojo names "Work Completion errors" as the consequence, but a specific completion status for this exact case — a rejection distinguishable from any other remote-access error, versus something less well-defined — is not stated anywhere found. Chapter 2.5 flagged the same gap for the general permission/bounds case; it applies here too, sharpened by timing.

**The specific race this chapter is about.** Permission and bounds violations (2.5) are static: an incoming operation's `rkey` resolves to a real, still-valid entry, and the check is whether the requested access matches that entry's permissions and range. Mid-transaction deregistration is dynamic: the entry itself stops being valid *while a resolved operation against it is still executing*. A remote RDMA write's `rkey` is checked once, early in the operation — the RETH carries it, the requester's RNIC looks it up against the MPT/MTT, and if the lookup succeeds, the operation proceeds to move data. That lookup and the DMA burst it authorizes are not necessarily the same instant. On any real implementation, a large write is not a single atomic act — it is a burst, plausibly split across multiple internal transfers, occupying some nonzero span of time on the PCIe/memory side after the rkey check has already passed. If `ibv_dereg_mr` runs on the local software stack during that span, the MPT/MTT entry the burst is still relying on can be invalidated out from under it — and per chapter 2.3's sourced finding from Kong et al., deregistration is suspected to invalidate the entire MTT/MPT cache's working set, not just the one entry being torn down, which makes the blast radius of a badly-timed deregistration considerably larger than "this one region becomes unavailable."

**What a hardware implementation has to decide, reasoned honestly.** Two shapes of answer are available, and nothing public commits to either for a real RNIC. One: the DMA engine, once it has validated an `rkey` and begun a burst, holds a private, already-resolved copy of the translation for the duration of that burst — the lookup happens once, the burst executes against a local copy, and a concurrent invalidation of the shared MPT/MTT entry (or the whole cache) simply doesn't reach an operation that's already past the check. This is the same shape of guarantee Part 8's DMA Engine chapter and this Part's caching chapters would need to describe explicitly if either committed to it, and neither does. Two: there is no such private copy, the DMA engine re-touches the shared table (or a cache line backed by it) at some granularity during a long burst — per sub-transfer, say — and a concurrent invalidation lands inside a live burst's execution window, producing a genuine race whose outcome (the burst faults partway through, silently continues against stale metadata, or something else) is undefined by any source this book found. Both are physically plausible designs. A private per-burst copy is the safer answer and the one that would make RDMAmojo's software contract sufficient in practice — software staying disciplined about *starting* a deregistration is enough, because hardware then finishes what it already started cleanly. A no-copy design would mean the software contract is necessary but not obviously sufficient — correct sequencing avoids triggering the race, but doesn't by itself prove there's no race to trigger if timing goes wrong. This book cannot resolve which of the two is true for any real RNIC, and says so plainly rather than picking the more comforting answer.

**Where this leaves the reader.** The pattern is identical to [Mid-Transaction QP Reset](/qp/mid-transaction-qp-reset)'s conclusion: the *problem* is real and, unusually for this Part's thinner corners, acknowledged in writing at the API-contract level. The *resolution mechanics* — what the DMA engine actually does when the table it depends on changes underneath an operation already in progress — sit past the edge of what any public source documents, for this resource exactly as much as for the QP.

> **Design rationale.** The honest way to reason about which of the two shapes above a real design would pick is to ask what a private per-burst translation copy would cost, since "always safer" isn't free. Holding a resolved translation locally for the life of a burst means the DMA engine needs somewhere to put it — a small per-in-flight-operation register or buffer, sized to whatever the maximum number of concurrent bursts the engine supports, not a large structure, but not nothing either, and it has to be populated at exactly the right moment (after the rkey check passes, before the burst can be preempted by anything else touching the shared table). The alternative — re-deriving the translation from the shared table at intervals during a long burst — costs nothing extra in dedicated storage, but reopens the same table on every re-touch to whatever churn is happening on it concurrently, including a deregistration event that chapter 2.3 already showed is disproportionately disruptive to that table's cache. Neither option is obviously dominant in the abstract; a design's actual choice would depend on typical burst length relative to expected deregistration frequency, and on how much silicon budget the vendor is willing to spend guaranteeing an invariant (in-flight operations are immune to concurrent table changes) that the verbs-layer software contract already tells applications not to rely on triggering in the first place. That last point cuts both ways: RDMAmojo's contract makes a hardware guarantee less *necessary* for correctness of well-behaved software, which is exactly the kind of pressure that could push a real vendor toward the cheaper, race-permitting design rather than the safer one — this book has no way to know which way any specific vendor actually went.

## Interface / timing reference

| Decision point | What a real design has to choose | This book's position |
|---|---|---|
| Stale-key access after deregistration, in general | Rely on software discipline vs. detect and safely reject in hardware | RDMAmojo states this is a software contract; hardware's specific behavior on violation is unstated |
| DMA burst already validated, deregistration concurrent | Private per-burst translation copy (immune to the race) vs. re-touching the shared table mid-burst (exposed to it) | Both physically plausible; not resolved by any public source |
| Blast radius of a concurrent deregistration | Invalidate one MPT/MTT entry vs. the whole cache | Kong et al. (ch. 2.3) reasons the whole cache is invalidated on this hardware — a materially wider window for the race above than a single-entry invalidation would create |
| Completion status on an actual stale-key hit | A distinguishable, specific error vs. an undefined/unspecified outcome | RDMAmojo names "Work Completion errors" generically; no specific status is documented for this exact case |

This is not a new class of problem. [Mid-Transaction QP Reset](/qp/mid-transaction-qp-reset) — Part 1's closing chapter — covers the same shape of hazard against a different resource: a Queue Pair reset with a packet, a replay-buffer entry, and a DMA write all still in flight against it, versus this chapter's Memory Region deregistered with a DMA burst still in flight against its key. Neither chapter can point at a documented resolution mechanism; both can point at exactly what has to be true for the outcome to be correct, and name the race that a real implementation has had to close one way or another.
