[One Transaction, Start to Finish](/overview/one-transaction-start-to-finish) already walked a Work Request from posting to wire, and named the doorbell that tells hardware new work exists without saying what, exactly, that work looks like sitting in memory. This chapter opens that box: the WQE itself, before any pipeline stage has touched it.

## Overview

A Work Queue Element (WQE) is, architecturally, nothing more exotic than a command descriptor in a producer-consumer ring -- the same shape as any descriptor written into a DMA engine's own descriptor ring or an accelerator's command queue. What's RDMA-specific is only the fields inside it, not the mechanism: what software actually writes into a Send Queue ring is a generic, transport-agnostic description of one operation -- an opcode, a scatter-gather list naming source bytes, and whatever remote-addressing fields that opcode needs. It is not the wire packet [What Is RoCEv2](/overview/what-is-rocev2) already described field by field, and it is not necessarily what a specific RNIC's own silicon stores on-chip either -- three distinct shapes sit between "software posts a request" and "a BTH/RETH/AETH packet leaves the port," and this chapter is about the first of them.

## Deep walkthrough

**What the standard actually requires, versus what a software-facing shape makes concrete.** IBTA-V1 specifies a Work Request's required content at a semantic level per opcode -- an RDMA Write names a remote address, an `rkey`, and a local data segment list; it does not specify a C struct, a field order, or a byte layout. A generic, transport-agnostic software descriptor is one concrete way of communicating that requirement to hardware, not the requirement itself. That distinction matters before going further: the standard sets what a Work Request must communicate; a software-facing descriptor shape is one way of communicating it; and, one layer further still below, a specific implementation's on-chip format is a third, independent thing again -- three different shapes this chapter is about to walk through, only one of which any standards body actually specifies.

**The software-facing shape, and what it deliberately doesn't commit to.** A generic work-request descriptor, the kind any transport-agnostic software API exposes to an application, is deliberately thin: a chaining mechanism for posting several requests in one call, a request identifier for matching a future completion back to this specific request, a scatter-gather list naming local source bytes (an address, a length, and the local key [The Memory Region Descriptor](/mr/the-memory-region-descriptor) already covers field by field), an opcode from the catalog [0.4](/overview/operation-catalog) already enumerated, a flags field, and either an immediate-data value or an invalidate-rkey value depending on which opcode this is. Nowhere in this shape is there a BTH, a PSN, or an ICRC -- those are hardware's job to produce, not software's job to supply. This is the same abstraction-boundary gap this book has already named at the doorbell ([0.5](/overview/one-transaction-start-to-finish)) and the QP table's internal organization ([2.2](/qp/the-qp-table)): a stable, checkable software-facing shape exists, and it is not a claim about what any specific RNIC stores internally.

**A real on-chip shape, shown specifically to make that gap concrete rather than asserted abstractly.** At least one shipped RNIC's on-chip control segment, confirmed directly against openly published low-level source rather than assumed, packs a WQE's control information into exactly four 32-bit fields: an opcode field, a combined field folding two pieces of information together (how many data segments this WQE carries, constrained to 6 bits, capping a single WQE at 63 data segments), a flags field, and a vendor-metadata field. Compare this to the software-facing shape's separate, independent segment-count field: the same information (how many scatter-gather entries this operation touches) exists in both shapes, but real hardware packs it into a shared, width-constrained field alongside an opcode, while the software-facing shape keeps it as its own untyped value. Neither shape is wrong -- they're solving different problems. Software's shape optimizes for a stable, transport-agnostic API surface across every vendor's hardware; a real on-chip shape optimizes for what actually fits efficiently into a fixed-width control segment a pipeline stage can parse in hardware. This is one confirmed, checkable example, not a claim that every RNIC packs a WQE control segment identically.

**Measured sizes -- concrete numbers, not qualitative gestures.** Kong et al. (NSDI 2023), measuring real ConnectX hardware directly, give this chapter its measured anchor: "A WQE for RC/UC is 36-byte, and 68-byte for UD." These are base sizes -- a control segment plus room for a minimal SGE fan-out, not a ceiling; the on-chip control segment's own segment-count field allows up to 63 data segments per WQE, so a WQE with heavy scatter-gather fan-out runs far past either base figure. UD's larger *base* size tracks directly with what [QP Context](/qp/qp-context) already established -- a UD QP names its destination per-message rather than once at connection setup, so its WQE has to carry addressing information RC/UC's WQE doesn't need, because RC/UC already fixed the destination QP number at INIT→RTR.

**The inline/DMA fork -- a fixed threshold with a concrete hardware consequence.** The same paper measures a "maximal inline size (28-byte)": a WQE whose payload fits within that threshold carries the payload bytes directly inside the WQE itself, avoiding a separate PCIe transaction to fetch it; a payload above that threshold requires the adapter to issue its own DMA read for the data, a mechanism [The Send Queue Ring](/tx/the-send-queue-ring) picks up from the fetch side and Part 8's DMA Engine owns in full. This is the first of several places in this Part where a small, fixed-size number determines whether an operation costs one memory transaction or two, and this distinction should carry forward rather than letting "the adapter fetches the WQE" stand as the end of the story.

**Where this is checked, and what happens next.** Nothing about the WQE's own fields is validated in isolation -- the opcode has to be one this QP's transport actually supports (Section [0.4](/overview/operation-catalog)'s catalog, gated by the QP's own transport type from [QP Context](/qp/qp-context)), the `lkey` on every SGE has to resolve against a permission-matching Memory Region entry ([The Key Table](/mr/the-key-table)), and the QP itself has to be in RTS ([QP State Machine](/qp/qp-state-machine)) before any of this is allowed to leave host memory at all. This chapter's job stops at naming what the WQE contains and how its shape differs from both the software struct above it and the wire packet below it; [The Send Queue Ring](/tx/the-send-queue-ring) is where a WQE actually gets fetched off the structure holding it.

> **Design rationale.** Keeping the software-facing WQE shape thin and transport-agnostic, rather than exposing a variant shaped to each vendor's actual on-chip packing, is what lets one software API target every RNIC vendor without an application recompiling against vendor-specific formats. The cost of that abstraction is paid entirely on the hardware side of the boundary: every real implementation has to translate a generic opcode-plus-scatter-gather-list shape into whatever dense, fixed-width packing its own pipeline can parse efficiently -- the four-32-bit-field control segment above is one confirmed example of paying that cost, not the only way to pay it. A vendor that instead exposed its literal on-chip WQE format as the API would save that translation step, at the cost of every application becoming vendor-locked to that one layout -- exactly the tradeoff RDMA's whole software model was built to avoid.

[The Send Queue Ring](/tx/the-send-queue-ring) is next: the structure that holds one of these WQEs per posted entry, and how hardware finds the next one to fetch.
