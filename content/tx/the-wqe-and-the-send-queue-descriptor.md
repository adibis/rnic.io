## Overview

A Work Queue Element (WQE) is, architecturally, nothing more exotic than a command descriptor in a producer-consumer ring. What's RDMA-specific is only the fields inside it, not the mechanism: what software actually writes into a Send Queue ring is a generic, transport-agnostic description of one operation -- an opcode, a scatter-gather list naming source bytes, and whatever remote-addressing fields that opcode needs. It is not the wire packet [What Is RoCEv2](/overview/what-is-rocev2) already described field by field, and it is not necessarily what a specific RNIC's own silicon stores on-chip either -- three distinct shapes sit between "software posts a request" and "a BTH/RETH/AETH packet leaves the port," and this chapter is about the first of them.

> [!WARNING] Analogy
> A WQE is the same shape as any descriptor written into a DMA engine's own descriptor ring or an accelerator's command queue -- a producer-consumer ring holding one command per entry, nothing about it specific to RDMA except which fields that command carries.

> [!NOTE] Concept
> Three distinct shapes sit between "software posts a request" and "a packet leaves the port": what the standard requires (semantic, per opcode), what a software-facing descriptor shape makes concrete (one way of communicating that requirement), and what a specific implementation's on-chip format actually is (a third, independent thing again). Only the first is ever specified by a standards body.

## Deep walkthrough

**What the standard actually requires, versus what a software-facing shape makes concrete.** IBTA-V1 specifies a Work Request's required content at a semantic level per opcode -- an RDMA Write names a remote address, an `rkey`, and a local data segment list; it does not specify a C struct, a field order, or a byte layout. A generic, transport-agnostic software descriptor is one concrete way of communicating that requirement to hardware, not the requirement itself. That distinction matters before going further: the standard sets what a Work Request must communicate; a software-facing descriptor shape is one way of communicating it; and, one layer further still below, a specific implementation's on-chip format is a third, independent thing again -- three different shapes this chapter is about to walk through, only one of which any standards body actually specifies.

**The software-facing shape, and what it deliberately doesn't commit to.** A generic work-request descriptor, the kind any transport-agnostic software API exposes to an application, is deliberately thin: a chaining mechanism for posting several requests in one call, a request identifier for matching a future completion back to this specific request, a scatter-gather list naming local source bytes (an address, a length, and the local key [The Memory Region Descriptor](/mr/the-memory-region-descriptor) already covers field by field), an opcode from the catalog [The Operation Catalog](/overview/operation-catalog) already enumerated, a flags field, and either an immediate-data value or an invalidate-rkey value depending on which opcode this is. Nowhere in this shape is there a BTH, a PSN, or an ICRC -- those are hardware's job to produce, not software's job to supply. This is the same abstraction-boundary gap this book has already named at the doorbell ([One Transaction, Start to Finish](/overview/one-transaction-start-to-finish)) and [The QP Table](/qp/the-qp-table)'s internal organization: a stable, checkable software-facing shape exists, and it is not a claim about what any specific RNIC stores internally.

**A real on-chip shape, shown specifically to make that gap concrete rather than asserted abstractly.** At least one shipped RNIC's on-chip control segment, confirmed directly against openly published low-level source rather than assumed, packs a WQE's control information into exactly four 32-bit fields: an opcode field, a combined field folding two pieces of information together (a send-queue identifier and how many data segments this WQE carries, the latter constrained to 6 bits, capping a single WQE at 63 data segments), a flags field, and a vendor-metadata field. Compare this to the software-facing shape's separate, independent segment-count field: the same information (how many scatter-gather entries this operation touches) exists in both shapes, but real hardware packs it into a shared, width-constrained field alongside a send-queue identifier, while the software-facing shape keeps it as its own untyped value. Neither shape is wrong -- they're solving different problems. Software's shape optimizes for a stable, transport-agnostic API surface across every vendor's hardware; a real on-chip shape optimizes for what actually fits efficiently into a fixed-width control segment a pipeline stage can parse in hardware. This is one confirmed, checkable example, not a claim that every RNIC packs a WQE control segment identically.

**Why "control segment" is the right name for it, not just a label this chapter chose.** A separate documented real implementation splits its own packed WQE into two explicit pieces -- a fixed-size control segment carrying exactly the fields above, followed by a variable-length data segment holding the SGE list or inline payload -- and only the control segment ever crosses the doorbell write itself, not the WQE's data segment. That split is the concrete reason a real WQE isn't one flat structure: the control segment is sized to fit whatever the doorbell mechanism can carry in one write, and the data segment -- SGEs or inlined bytes -- trails behind it in the ring, fetched or read separately. This chapter treats it as a second, independently sourced data point alongside Kong et al.'s field count above, not a claim that the two describe the identical structure.

**What the flags field actually carries.** That field isn't a placeholder -- four independent, opcode-agnostic requests live there, each changing how this operation is scheduled, reported, or handled rather than what it does. An ordering request, commonly called a *fence*, holds this Work Request's own issue until every earlier RDMA read and atomic operation posted to the same Send Queue has completed -- RDMAmojo's documentation states the guarantee directly: fencing "guarantees the processing order and Completion notification of Send Requests that were posted to the same Send Queue." It's a purely local scheduling constraint; nothing about it reaches the wire. A completion-request flag selects whether this specific operation generates a completion at all once it finishes, since an application doesn't need a Completion Queue entry for every operation it posts, only the ones it actually intends to wait on -- also purely local. A solicited-event request is the one flag here that does reach the wire: it's what sets BTH's SE bit ([What Is RoCEv2](/overview/what-is-rocev2)), asking the *responder* to notify its application through an asynchronous event rather than leave it to find the completion by polling. An inline request asks hardware to copy the payload directly into the WQE itself rather than leave it in the source buffer for a later DMA read -- covered in depth two paragraphs below, since it's the one flag with a hardware-enforced size ceiling attached to it. [Single-QP Pipeline Stalls](/tx/single-qp-pipeline-stalls) picks the fence request back up as a real stall cause; this chapter's job is just naming that all four exist as flags a Work Request carries.

**Measured sizes -- concrete numbers, not qualitative gestures.** Kong et al. (NSDI 2023), measuring real ConnectX hardware directly, give this chapter its measured anchor: "A WQE for RC/UC is 36-byte, and 68-byte for UD." These are base sizes -- a control segment plus room for a minimal SGE fan-out, not a ceiling; the on-chip control segment's own segment-count field allows up to 63 data segments per WQE, so a WQE with heavy scatter-gather fan-out runs far past either base figure. UD's larger *base* size tracks directly with what [QP Context](/qp/qp-context) already established -- a UD QP names its destination per-message rather than once at connection setup, so its WQE has to carry addressing information RC/UC's WQE doesn't need, because RC/UC already fixed the destination QP number at INIT→RTR.

**The inline/DMA fork -- a software request, with a fixed threshold enforcing it.** Inline placement isn't something hardware decides unprompted by payload size alone -- it's a request software makes via the inline flag named above, and the same paper measures the ceiling that request is checked against: a "maximal inline size (28-byte)." A payload within that threshold, requested inline, gets copied directly into the WQE itself, avoiding a separate PCIe transaction to fetch it later; a payload above the threshold can't be inlined regardless of the flag, and falls to the adapter issuing its own DMA read for the data instead, a mechanism [The Send Queue Ring](/tx/the-send-queue-ring) picks up from the fetch side and [DMA Engine](/dma/)'s DMA Engine owns in full. Inline carries two real consequences beyond just skipping a memory transaction: the payload is never referenced by an SGE at all, so there's no `lkey` to check against the Key Table for it, and the source buffer is safe for software to reuse the instant the post call returns, since hardware has already copied the bytes it needs rather than deferring a read against memory software might otherwise overwrite. It's the first of several places in this part where a small, fixed-size number decides whether an operation costs one memory transaction or two -- "the adapter fetches the WQE" isn't the end of the story.

**Where this is checked, and what happens next.** Nothing about the WQE's own fields is validated in isolation -- the opcode has to be one this QP's transport actually supports ([The Operation Catalog](/overview/operation-catalog), gated by the QP's own transport type from [QP Context](/qp/qp-context)), the `lkey` on every SGE has to resolve against a permission-matching Memory Region entry ([The Key Table](/mr/the-key-table)) -- except an inlined payload, which carries no SGE and so has no `lkey` to check at all -- and the QP itself has to be in RTS ([QP State Machine](/qp/qp-state-machine)) before any of this is allowed to leave host memory at all. This chapter's job stops at naming what the WQE contains and how its shape differs from both the software struct above it and the wire packet below it; [The Send Queue Ring](/tx/the-send-queue-ring) is where a WQE actually gets fetched off the structure holding it.

> [!TIP] Why
> Keeping the software-facing WQE shape thin and transport-agnostic, rather than exposing a variant shaped to each vendor's actual on-chip packing, is what lets one software API target every RNIC vendor without an application recompiling against vendor-specific formats. The cost of that abstraction is paid entirely on the hardware side of the boundary: every real implementation has to translate a generic opcode-plus-scatter-gather-list shape into whatever dense, fixed-width packing its own pipeline can parse efficiently -- the four-32-bit-field control segment above is one confirmed example of paying that cost, not the only way to pay it. A vendor that instead exposed its literal on-chip WQE format as the API would save that translation step, at the cost of every application becoming vendor-locked to that one layout -- exactly the tradeoff RDMA's whole software model was built to avoid.

## Field reference

Every field a Work Request carries, and how much of each one IBTA-V1 actually pins down versus leaves to whoever designs the software-facing interface. "Architect's choice" doesn't mean arbitrary -- it means the standard requires the capability to exist without mandating this particular shape for it, and every real interface converges on something close to what's below because the underlying requirement is the same one.

| Field | Carries | Standard's role |
|---|---|---|
| **WR ID** | opaque value, echoed back on the matching completion | architect's choice -- IBTA-V1 requires a completion be traceable to its request, not this exact mechanism |
| **next** | pointer chaining several Work Requests into one post call | architect's choice |
| **opcode** | which operation this WR requests | IBTA-V1 -- [The Operation Catalog](/overview/operation-catalog) enumerates the full set |
| **SGE list** | local source bytes: address, length, `lkey` -- absent entirely if inline is set | IBTA-V1 requires the semantic content (source bytes, a checkable permission); this exact shape is architect's choice |
| **remote addr / rkey** | where an RDMA operation lands on the responder | IBTA-V1 -- mirrored directly in RETH on the wire |
| **immediate data / invalidate rkey** | one union value, which one depends on the opcode | IBTA-V1 |
| **flags** | four independent per-WR requests -- broken out below, not repeated here | see below |

**What's inside `flags`.** The flags field above contains the following four requests:

| Flag | Requests | Standard's role |
|---|---|---|
| **fence** | hold this WR's issue until every earlier read/atomic on the same Send Queue completes | IBTA-V1 requires the ordering guarantee be expressible; this flag shape is architect's choice |
| **signal** | this WR generate a completion at all | IBTA-V1 requires selective completion generation be possible; this flag shape is architect's choice |
| **solicit** | the responder wake its application via an event, not a silent completion | IBTA-V1 -- sets BTH's SE bit, a defined wire field |
| **inline** | the payload be copied into the WQE itself, skipping the `lkey` check and a later DMA read | architect's choice -- a real optimization no source ties to IBTA-V1's own text |
